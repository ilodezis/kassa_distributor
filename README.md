# Kassa Distribution Tool

Десктопное приложение для распределения касс между менеджерами сопровождения. Берёт выгрузку из Excel, раскладывает кассы в два этапа — точное выравнивание по количеству, затем правка тарифного микса обменами — и показывает результат: итоги по менеджерам, лог перемещений, проверки и график.

Интерфейс и вся логика написаны на TypeScript, оболочка — Tauri. Собирается в GitHub Actions под macOS (Apple Silicon) и Windows (x64).
## Возможности

- Балансировка по менеджерам: количество касс выравнивается **точно** (разброс 0), тарифы 1/3/12 месяцев — с точностью до округления таргетов (обычно ±1).
- Редактор менеджеров: роли (`support`), индивидуальные лимиты (`cap`), массовое редактирование через multi-select (клик, Ctrl/Cmd, Shift).
- Настройки команды хранятся в файле `managers.json` в папке данных приложения, не в коде и не внутри `.app`. Изменения сохраняются сами. Есть импорт старого `managers.json` от Python-версии.
- Минимум миграций: текущие привязки сохраняются где возможно, оплаченные кассы не трогаются.
- Экспорт в Excel (итоговое распределение, summary, лог перемещений, лог проверок) и график результата.

## Правила распределения

0. **Менеджер — это почта.** Кассы сопоставляются с `managers.json` по `Почта текущего менеджера`; ФИО только для показа (в выгрузке оно плавает: порядок слов, логин вместо имени).
1. **Заморозка оплат.** Если `Статус оплаты = paid` и касса уже на менеджере сопровождения — не перемещается.
1a. **Заморозка расторжений и незнакомых статусов.** Касса с заполненной `Дата расторжения` или со статусом оплаты не из `paid`/`topay` остаётся на текущем менеджере, в раскладке и в нагрузке не участвует и перечисляется в логе проверок (ИНН, менеджер, причина).
2. **Внешний пул.** Кассы на менеджерах не из сопровождения (оплаченные и нет) принудительно переносятся в сопровождение.
3. **Индивидуальные лимиты.** Кассы равномерно распределяются между менеджерами с лимитом (до их cap) и без лимита.
4. **Консервативный ребаланс.** Неоплаченные кассы внутри сопровождения двигаются по минимуму: кто уже сидит на менеджере и влезает в его таргет — остаётся на месте.

## Как работает алгоритм

Раскладка идёт в два этапа с разными задачами. Они не конкурируют между собой: этап 2 по построению не может испортить результат этапа 1.

**1. Расчёт таргетов.** Для каждого support-менеджера считается справедливая доля: `всего касс / число менеджеров`, обрезанная по `cap`, если он задан, и не ниже уже зафиксированных (оплаченных) касс. Дробные остатки округляются методом наибольшего остатка (largest remainder), чтобы сумма таргетов точно совпала с общим числом касс. Таргет по каждому тарифу внутри менеджера считается так же — от глобальной доли этого тарифа во всей выгрузке.

**2. Этап 1 — точное попадание по количеству.** Каждый менеджер получает ровно свой таргет. Это не оптимизация, а арифметика: сумма таргетов равна числу касс, ни у кого таргет не ниже замороженных оплат, значит свободный пул в точности покрывает суммарную нехватку и раскладка всегда сходится. **Разброс по общему количеству получается нулевым по построению, а не по итогам сходимости.** Кассы, которые уже стоят на менеджере и влезают в его таргет, остаются на месте — лог перемещений от этого не распухает. Тариф на этом этапе используется только как тайбрейк при выборе получателя.

**3. Этап 2 — тарифный микс парными обменами.** Менеджер A отдаёт кассу тарифа X, менеджер B одновременно отдаёт кассу тарифа Y. Количество касс у обоих сохраняется, поэтому обмены физически не могут сдвинуть итоги, выставленные этапом 1. Цель — минимум суммы квадратов отклонений от тарифных таргетов; проход повторяется, пока хоть один обмен улучшает результат. Двигаются только неоплаченные кассы.

**Почему без «допусков» в самой модели.** Штраф — просто квадрат отклонения, без мёртвой зоны, поэтому модель дожимает до арифметического предела. Константы `TOTAL_TOLERANCE` (±5) и `PERIOD_TOLERANCE` (±3) нужны только как пороги в логе проверок и как запас сверх `cap` при расчёте таргетов.

**Чего алгоритм не делает.** Этап 2 — локальный поиск: он останавливается, когда ни один парный обмен не улучшает микс, и глобальный минимум по тарифам не гарантирован (на практике упирается в ±1, то есть в округление таргетов). Оплаченные кассы заморожены правилом 1, поэтому тарифный перекос, целиком состоящий из оплат, обменами не лечится.

**Порядок обхода — часть алгоритма.** Результат зависит от порядка строк и менеджеров и от тайбрейков (наибольший остаток, выбор получателя на этапе 1, порядок пар на этапе 2). Они перенесены из прежней Python-версии один в один; менять их можно только осознанно — «золотые» тесты тогда придётся обновить.

## Разработка

Нужны Node.js (последняя LTS) и Rust (stable).
```bash
npm install
npm run tauri dev      # приложение в окне, с горячей перезагрузкой
npm run dev            # только интерфейс в браузере (файлы и конфиг — через браузер)
npm test               # тесты
npm run typecheck
npm run tauri build    # собрать приложение под текущую систему
```

Ядро (`src/core/`) не зависит ни от DOM, ни от Tauri: его гоняют тесты, интерфейс и скрипт сверки.

## Сборка под macOS и Windows

Workflow `.github/workflows/ci.yml`:

- на каждый push в `main` и pull request — типизация и тесты;
- вручную (Actions → ci → Run workflow) или на тег `v*` — после тестов собираются два артефакта: **`.dmg` для Apple Silicon** (macOS-раннер) и **установщик `.exe` для Windows x64**. Из ручного запуска файлы забираются как артефакты, на тег они ещё и прикрепляются к релизу. Сборки под Intel-мак нет.

Приложение не подписано сертификатом Apple (подпись ad-hoc), поэтому при первом запуске macOS попросит разрешить его: правый клик по приложению → «Открыть» или «Настройки → Конфиденциальность и безопасность → Всё равно открыть».

Установщик Windows тоже без подписи: SmartScreen покажет «Windows защитила ваш компьютер» — «Подробнее» → «Выполнить в любом случае».

Минимальная версия macOS — 12.3.

## Формат входного Excel

Выгрузка `renewal-distribution-YYYY-MM.xlsx`, читается первый лист. Обязательные колонки:

| Колонка | Значения |
|---|---|
| `Почта текущего менеджера` | ключ менеджера |
| `ФИО текущего менеджера` | для показа и для привязки старых записей конфига |
| `Тариф` | `1`, `3` или `12` (месяцев) |
| `Статус оплаты` | `paid` — оплачена, `topay` — нет, остальное замораживается |

Необязательные, но учитываемые: `ИНН` (читается текстом, ведущие нули сохраняются) и `Дата расторжения` (заполнена — касса замораживается). Остальные колонки выгрузки программа не трогает и переносит в результат как есть. Старый формат (`Менеджер` / `Оплачен ИНН`) не поддерживается.

## Как пользоваться

1. «Загрузить Excel» — выбери выгрузку. Менеджеры из неё сразу попадут в список.
2. Во вкладке «Менеджеры» отметь участников сопровождения и задай лимиты (cap), если нужно. Кнопка «Подтянуть менеджеров из Excel» добавит тех, кого в списке ещё нет.
3. «Запустить распределение».
4. Проверь вкладки Summary, Moves, Checks и Chart.
5. «Сохранить результат» — результат в Excel.

Результат — файл с листами `result` (исходные данные + колонки `Почта нового менеджера` и `Новый менеджер`), `summary`, `moves` (лог перемещений с ИНН) и `checks` (лог проверок на логические ошибки, замороженные кассы, support без почты).

## managers.json

Список менеджеров с ролью и лимитом. Редактируется во вкладке «Менеджеры» и сохраняется сам. Лежит в папке данных приложения:

| Система | Путь |
|---|---|
| macOS | `~/Library/Application Support/io.github.ilodezis.kassa-distributor/managers.json` |
| Windows | `%APPDATA%\io.github.ilodezis.kassa-distributor\managers.json` |

Формат тот же, что был у Python-версии (version 2):

```json
{
  "version": 2,
  "managers": [
    { "email": "i.ivanov@cp.ru", "name": "Иванов Иван Иванович", "is_support": true, "has_cap": false, "cap": null },
    { "email": "p.petrov@cp.ru", "name": "Петров Пётр Петрович", "is_support": true, "has_cap": true, "cap": 150 }
  ]
}
```

- `email` — ключ, должен совпадать с `Почта текущего менеджера` в выгрузке.
- `is_support` — участвует ли менеджер в распределении (кассы не-support менеджеров всегда переносятся в пул).
- `has_cap` / `cap` — потолок по количеству касс на менеджера (с запасом +5 в проверках).

**Импорт старого `managers.json`.** Вкладка «Менеджеры» → «Импортировать managers.json…». Python-сборка для macOS хранила файл в `~/Library/Application Support/KassaDistributor/managers.json` — диалог открывается сразу там. Старый конфиг (version 1, без почт) читается как есть: когда загружена выгрузка, запись получает почту, если её `name` точно совпал с ФИО. Несовпавшие support-записи в раскладке не участвуют и перечисляются в логе проверок — почту им вписывает распределяющий (или удаляет запись и настраивает строку из выгрузки).

**Выгрузка — реальные данные: в git её не класть** (`*.xlsx` в `.gitignore`).

«Золотые» файлы `tests/golden/*.json` — замороженные синтетические выгрузки и ожидаемый результат; `tests/golden.test.ts` сверяет с ними распределение.

## Структура проекта

```text
src/core/              логика без DOM и Tauri
  distribute.ts        таргеты, этап 1, этап 2, summary, проверки
  config.ts            managers.json: чтение, нормализация, привязка старых записей
  editor.ts            правила редактора менеджеров
  table.ts, xlsx.ts    выгрузка → таблица, результат → xlsx
  pystr.ts             Python-совместимые строки и числа (там, где JS отличается)
src/ui/                интерфейс: вкладки, таблицы, график, диалоги
src/platform/          файлы и диалоги: Tauri и браузерный вариант
src-tauri/             оболочка Tauri (Rust): окно, права, иконки
tests/                 тесты и «золотые» файлы
```

## Тесты

```bash
npm test
```

Проверяют, что разброс по количеству нулевой, тарифы в допуске, обмены не меняют итоги, оплаченные кассы не сдвинуты, кассы не теряются, лимиты соблюдены, замороженные строки не двигаются, ИНН не теряет ведущий ноль, конфиг лежит в папке данных, а не в бандле; плюс сверка с «золотыми» файлами.
